# 架构说明

## 项目定位

Path of Market（市场之路）是一个包含研究 Agent 的个人财经研究工作台。产品负责组织资料、研究记录和交互；研究 Agent 根据用户目标选择工具、读取证据，并决定是否继续调查。它不替用户做投资决策。

第一版在本机运行，用浏览器访问。网页界面与后端服务共同组成完整应用，部署方式不决定它是否具备 Agent 行为。

## 总体架构

```text
用户
  -> apps/web 前端操作台
    -> apps/server Java 主后端
      -> apps/agent Python Agent 服务
        -> 研究状态 + 模型决策 + 有边界的工具调用循环
          -> 文档检索 / 文档读取 / 行情查询 / 数值计算
            -> Data Provider / 本地资料 / 数据 API
```

## 三个应用

| 应用 | 技术 | 职责 |
| --- | --- | --- |
| `apps/web` | React + Vite + TypeScript | 页面、表单、按钮、报告展示、用户交互 |
| `apps/server` | Java + Spring Boot | 主 API、数据库、用户画像、研究日志、观察池、任务状态 |
| `apps/agent` | Python + FastAPI | LLM 调用、RAG、文档解析、工具调用、Agent 工作流 |

## 关键原则

- 前端通常只调用 Java 主后端，不直接调用 Python Agent 服务。
- Java 主后端是系统中枢，负责稳定业务和数据持久化。
- Python Agent 服务是智能能力层，负责模型、检索、工具和工作流。
- 数据源必须通过 Data Provider 封装，避免业务逻辑绑定某个网站或 API。
- 每个任务聊天框只做一个小功能，避免一次性大改。
- 模型供应商和数据源通过独立接口接入，供工作台与未来研究 Skill 共用。
- 研究状态记录对象、问题、截止日期、用户偏好、预兆、证据和工具执行结果。
- 数值计算、公司和日期过滤由确定性程序承担；模型负责选择研究动作和解释证据。
- 行情和财务表通过查询、计算工具读取；文档检索负责找到原文证据，不把所有数据都塞进向量索引。
- 来源至少记录资料名称、来源链接或文件标识、披露日期；PDF 证据还要尽量保留页码。

## 真实研究 Agent 的核心循环

```text
研究目标 + 用户偏好 + 预兆 + 已有证据
  -> 模型决定下一步研究动作
    -> 程序校验并执行允许的工具
      -> 工具结果和来源进入研究状态
        -> 模型继续判断：补查 / 对比 / 完成
```

运行框架控制步数、费用和超时，避免无限查询。模型无法获得足够资料时，应输出缺口；遇到限制时记录停止原因。运行记录展示工具动作与证据，不要求披露模型的内部思维过程。

追猎者可以由定时任务唤醒；唤醒后哪些变化值得调查、调用哪些资料工具，由研究 Agent 根据结果决定。锐眼结合用户偏好决定调查重点，并给出有证据的相关性说明。

四个预兆是研究策略配置，影响任务、资料和检查项目。第一版不要求四个独立模型或四个独立 Agent。详见 `report-omens.md`。

## 实施顺序

| 阶段 | 目标 | 完成的含义 |
| --- | --- | --- |
| M0 | 完整应用骨架 | 网页经 Java 调用 Python，输入研究对象后展示演示报告 |
| M1 | 真实研究 Agent v0 | 模型能实际选择工具，依据结果补查或结束，输出可核查证据 |
| M2 | 研究积累与资料完善 | 保存报告、来源、运行记录和画像，完善检索与展示 |
| M3 | 板块地图、追踪与筛选 | 变化能关联既有判断与个人偏好，扩展研究 Skill |

先完成原设计中的网页、Java、Python 最小闭环，使用演示结果检查通信和报告格式；之后在同一应用中接入真实研究能力。M1 的初始资料可限制为少量公司、少量真实公开报告，不需要先建全市场数据库。

## M0-1：已完成的 Python 服务

状态：2026-10-13 已完成并通过实际 HTTP 检查。接口、启动方法和验证结果见 `first-step.md`。Java 启动也已在 M0-2 完成，下一项为 M0-3 Java 调用 Python。

第一步只启动 Python 服务：

```text
HTTP 请求
  -> Python 校验研究输入
    -> 生成明确标记为 mock 的演示结构
      -> 返回 JSON 报告
```

M0 的完成不能标记为 M1 完成，也不能声称已经进行真实资料研究。

## M0-2：已完成的 Java 主后端启动

状态：2026-10-13 已完成，Spring Boot 编译打包和实际 HTTP 检查通过。Java 提供自身健康接口 `GET /api/health`，默认只监听 `127.0.0.1:8080`。启动方法和验证结果见 `second-step.md`。

Java 当前可以独立启动，尚未调用 Python。M0-3 将在现有主后端中接入 Python 的演示研究接口，沿用网页 → Java → Python 的职责边界。

## M0：前端与两个后端的最小闭环

后续需要打通：

```text
前端输入研究对象
  -> Java 接收请求
    -> Java 调 Python /research/mock 接口
      -> Python 返回明确标记为演示的结构化报告
    -> Java 转发结果
  -> 前端展示报告
```

验收标准：

- 前端能打开页面并提交研究对象、问题、偏好和预兆。
- Java 主后端能提供 `/api/health`，并调用 Python 服务。
- 页面明确区分演示结果与真实研究结果。
- 演示结果不编造真实来源和工具记录。
- M1 接入真实研究后，再显示实际引用来源和工具执行记录。
