# 架构说明

## 项目定位

Path of Market（市场之路）是一个包含研究 Agent 的个人财经研究工作台。产品负责组织资料、研究记录和交互；研究 Agent 根据用户目标选择工具、读取证据，并决定是否继续调查。它不替用户做投资决策。

第一版在本机运行，用浏览器访问。网页界面与后端服务共同组成完整应用，部署方式不决定它是否具备 Agent 行为。

## 总体架构

```text
用户
  -> apps/web 前端操作台
    -> apps/server Java 主后端
      -> apps/agent Python Agent 服务
        -> 研究状态 + 模型决策 + 有边界的工具调用循环
          -> 文档检索 / 文档读取 / 行情查询 / 数值计算
            -> Data Provider / 本地资料 / 数据 API
```

## 三个应用

| 应用 | 技术 | 职责 |
| --- | --- | --- |
| `apps/web` | React + Vite + TypeScript | 页面、表单、按钮、报告展示、用户交互 |
| `apps/server` | Java + Spring Boot | 主 API、数据库、用户画像、研究日志、观察池、任务状态 |
| `apps/agent` | Python + FastAPI | LLM 调用、RAG、文档解析、工具调用、Agent 工作流 |

## 研究运行架构与报告能力

`research-runtime-plan.md` 将现有分层进一步拆为 ContextBuilder、ModelAdapter、ToolRegistry/Executor、Runner、研究状态与记忆、ReportComposer 和图表渲染。各部件标明当前状态与实施阶段；这是补充设计，三应用架构与原阶段顺序不变。

Agent 核心机制先核对成熟开源实现或官方文档，依据与状态见 `agent-design-decisions.md`。按用户要求采用 JSONL 追加会话、节点父关系与当前分支上下文方向：Python 产生事件，Java SessionStore 负责业务持久化；会话与恢复分阶段实现。所有选定原始资料默认完整分批阅读，记录实际覆盖，关键词只作回查。

正式研究报告需要有来源的表格与图表，长报告采用分章生成、保存、整合和续写。上下文窗口、单次输出与整份研究预算分别管理；当前 M1-1 的短 JSON 与单次 token 校验不是最终报告规格。

截至 2026-10-24，M1-3 已接入真实模型工具循环、全文文字批次处理、进程内异步任务和股票日线图表。`AgentRunner` 暴露三个逻辑工具，复用七个底层工具；Java 代理创建/查询/取消任务，网页轮询。通用报告块、会话落盘、上下文压缩和长报告仍待做，见 `m1-3-agent.md`。

同日按用户优先要求补充：当前为五个逻辑工具/八个底层工具，增加原页视觉和原版Skill参考读取；实际加载公司财务研究Skill，核心财务底稿由程序计算同比并驱动图表/表格。`AgentRunner.context` 对旧结果去重并传一份当前底稿，不等于M2自动历史压缩。细节与第三方许可见 `financial-research-skill.md`。

## 关键原则

- 前端通常只调用 Java 主后端，不直接调用 Python Agent 服务。
- Java 主后端是系统中枢，负责稳定业务和数据持久化。
- Python Agent 服务是智能能力层，负责模型、检索、工具和工作流。
- 数据源必须通过 Data Provider 封装，避免业务逻辑绑定某个网站或 API。
- 每个任务聊天框只做一个小功能，避免一次性大改。
- 模型供应商和数据源通过独立接口接入，供工作台与未来研究 Skill 共用。
- 研究状态记录对象、问题、截止日期、用户偏好、预兆、证据和工具执行结果。
- 数值计算、公司和日期过滤由确定性程序承担；模型负责选择研究动作和解释证据。
- 行情和财务表通过查询、计算工具读取；文档检索负责找到原文证据，不把所有数据都塞进向量索引。
- 来源至少记录资料名称、来源链接或文件标识、披露日期；PDF 证据还要尽量保留页码。

## 真实研究 Agent 的核心循环

```text
研究目标 + 用户偏好 + 预兆 + 已有证据
  -> 模型决定下一步研究动作
    -> 程序校验并执行允许的工具
      -> 工具结果和来源进入研究状态
        -> 模型继续判断：补查 / 对比 / 完成
```

运行框架控制步数、费用和超时，避免无限查询。模型无法获得足够资料时，应输出缺口；遇到限制时记录停止原因。运行记录展示工具动作与证据，不要求披露模型的内部思维过程。

追猎者可以由定时任务唤醒；唤醒后哪些变化值得调查、调用哪些资料工具，由研究 Agent 根据结果决定。锐眼结合用户偏好决定调查重点，并给出有证据的相关性说明。

四个预兆是研究策略配置，影响任务、资料和检查项目。第一版不要求四个独立模型或四个独立 Agent。详见 `report-omens.md`。

## 实施顺序

| 阶段 | 目标 | 完成的含义 |
| --- | --- | --- |
| M0 | 完整应用骨架 | 网页经 Java 调用 Python，输入研究对象后展示演示报告 |
| M1 | 真实研究 Agent v0 | 模型能实际选择工具，依据结果补查或结束，输出可核查证据 |
| M2 | 研究积累与资料完善 | 保存报告、来源、运行记录和画像，完善检索与展示 |
| M3 | 板块地图、追踪与筛选 | 变化能关联既有判断与个人偏好，扩展研究 Skill |

先完成原设计中的网页、Java、Python 最小闭环，使用演示结果检查通信和报告格式；之后在同一应用中接入真实研究能力。M1 的初始资料可限制为少量公司、少量真实公开报告，不需要先建全市场数据库。

## M1-3：已完成的动态循环与行情图表

Python `services/agent_runner.py` 组装任务、规则、工具和前序结果，处理原生 `tool_calls`，保留模型调用 ID；`read_document(full)` 通过底层工具下载并连续分批处理 PDF 文字，按成功批次记录覆盖。`tools/market.py` 从主备 Provider 获取同源两种价格口径并计算确定性指标。最终检查来源/覆盖，再复核正文口径。

`POST /api/research/jobs` 经 Java 对应 Python `/research/jobs`，立即返回任务 ID；GET 查询状态与结果，DELETE 取消。Java `AgentJobClient` 对短请求、完整正文等待和响应结构设边界。React `ResearchWorkspace` 轮询并恢复进程内任务，`ResearchReport` 与 `MarketChart` 展示引用、覆盖、工具、真实曲线和指标表。浏览器不直接请求 Python 或模型账户。

目前任务/事件只在 Python 进程内，最多保留八个任务、同时运行一个。`id/parentId` 预留未来追加/分支，但没有 JSONL 文件、完整会话重载、分支 UI 或自动上下文摘要。阅读缓存是派生资料，不能替代 SessionStore。三份中际旭创 PDF 共 649 页文字、486 个交易日实际案例与检查见 `m1-3-agent.md`。

## M0：前端与两个后端的最小闭环（历史验收）

M0-5 已验证以下功能链路：

```text
前端输入研究对象
  -> Java 接收请求
    -> Java 调 Python /research/mock 接口
      -> Python 返回明确标记为演示的结构化报告
    -> Java 转发结果
  -> 前端展示报告
```

验收标准：

- 前端能打开页面并提交研究对象、问题、偏好和预兆。
- Java 主后端能提供 `/api/health`，并调用 Python 服务。
- 页面明确区分演示结果与真实研究结果。
- 演示结果不编造真实来源和工具记录。
- M1 接入真实研究后，再显示实际引用来源和工具执行记录。
