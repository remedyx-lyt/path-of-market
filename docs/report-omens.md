# 研究报告预兆

## 定位

研究报告预兆是深研室的可选报告增强机制。它借用《流放之路 2》中“预兆”的意象：预兆不是替用户决定结果，而是在生成报告前改变研究视角和输出权重。

用户生成公司或行业研究报告时，可以选择 0 个、1 个或多个预兆。多个预兆可以叠加，但系统必须在报告中说明本次报告采用了哪些观察角度。

## 设计原则

- 预兆只改变研究侧重点，不直接给出买卖建议。
- 每个预兆都要影响任务拆解、资料选择、报告结构和自检标准。
- 多个预兆叠加时，报告需要平衡不同视角，避免只强化单一结论。
- 所有关键结论都必须尽量附带来源、证据或可追溯依据。
- 每个预兆都不能只写成一句泛泛的 prompt 约束。后续实现时，每个预兆都应该有较完整的研究规格，确保生成结果真正符合主题。
- 多个预兆叠加时，不应为了控制篇幅而明显牺牲任何一个预兆的分析质量。Path of Market（市场之路）默认偏向生成完整、详细、可追溯的研究报告。

## 预兆规格模板

后续实现每个预兆时，至少应该补齐以下内容：

| 字段 | 说明 |
| --- | --- |
| 核心目标 | 这个预兆到底要让报告多看见什么 |
| 适用场景 | 什么类型的公司、行业或研究问题适合使用 |
| 资料偏好 | 应该优先寻找哪些资料，例如财报、公告、历史案例、政策、新闻、行业数据 |
| 任务拆解要求 | 规划阶段必须拆出哪些子任务 |
| 报告章节要求 | 最终报告必须增加或强化哪些章节 |
| 关键问题清单 | Agent 必须回答的一组问题 |
| 自检标准 | 报告生成后如何检查这个预兆是否真正生效 |
| 禁止事项 | 哪些写法不允许，例如空泛展望、无证据推断、把可能性写成确定性 |

第一版实现时也应该尽量按这个模板写，而不是只在 prompt 中追加一句泛泛要求。

## 四个第一版预兆

| 预兆 | 侧重点 | 用途 |
| --- | --- | --- |
| 崇高预兆 | 深入解读 | 对公司、行业、商业模式、财务质量、竞争格局做更细的结构化拆解 |
| 远古预兆 | 历史参照 | 从历史周期、过往相似案例、行业演化、公司关键转折中寻找参照 |
| 机遇预兆 | 未来变化 | 更侧重未来趋势、潜在催化、技术变化、政策变化、需求变化和情景推演 |
| 深渊回响预兆 | 风险端 | 更侧重风险、反方论点、估值陷阱、周期下行、财务压力和黑天鹅线索 |

## 完整预兆规格

### 崇高预兆

代码标识：`exalted`

核心目标：让报告从“知道这家公司或行业是什么”升级到“理解它为什么这样运转”。崇高预兆要强化深度解释，重点拆解商业模式、利润结构、财务质量、竞争优势、行业位置和关键指标含义。

适用场景：

- 用户第一次系统研究一家公司或行业。
- 用户想理解公司长期价值、护城河、利润来源或经营质量。
- 研究对象业务复杂，例如多业务集团、平台型公司、产业链龙头、金融公司、科技公司。
- 用户已经知道基本新闻，但不知道如何把信息组织成研究框架。

资料偏好：

- 年报、季报、招股书、投资者关系材料。
- 公司公告、管理层讨论与分析、电话会纪要。
- 行业报告、竞品资料、产业链资料。
- 财务指标、分部收入、毛利率、费用率、现金流、资本开支、负债结构。
- 公开访谈、产品资料、客户结构、供应链信息。

任务拆解要求：

1. 拆解公司或行业的基本结构：业务线、产业链位置、客户、供应商、渠道。
2. 解释赚钱方式：收入来自哪里，成本在哪里，利润由哪些因素驱动。
3. 分析关键指标：哪些指标真正影响价值，指标变化说明什么。
4. 比较竞争格局：主要竞争者是谁，优势和劣势分别是什么。
5. 判断经营质量：盈利质量、现金流质量、资产负债质量、管理层执行力。
6. 给出研究结论边界：哪些地方已经有证据，哪些地方仍然缺资料。

报告章节要求：

- 商业模式拆解。
- 利润与现金流驱动因素。
- 竞争格局与护城河。
- 关键指标解释。
- 财务质量观察。
- 仍需继续验证的问题。

关键问题清单：

- 这家公司或行业到底如何赚钱？
- 收入增长主要靠价格、销量、渗透率、周期、并购，还是新业务？
- 毛利率和净利率由什么决定？
- 现金流是否支持利润质量？
- 公司真正的竞争优势是什么，它是否可持续？
- 关键风险是否已经反映在经营数据里？
- 如果只追踪 3 到 5 个指标，应该追踪哪些？

自检标准：

- 报告不能只罗列事实，必须解释事实之间的因果关系。
- 至少要有一段“关键指标为什么重要”的解释。
- 至少要指出 2 个以上仍需继续验证的问题。
- 如果涉及财务判断，必须区分利润、现金流和资产负债表。
- 如果使用“护城河”“龙头”“高质量”等词，必须说明依据。

禁止事项：

- 禁止只写公司简介和新闻摘要。
- 禁止把收入增长直接等同于经营质量提升。
- 禁止在没有证据时断言“护城河稳固”或“长期空间巨大”。
- 禁止忽略现金流、负债和资本开支。
- 禁止给出买入、卖出、持有等投资建议。

### 远古预兆

代码标识：`ancient`

核心目标：让报告从当前截面回到历史长河中观察。远古预兆要强化历史参照，寻找相似周期、过往案例、行业演化、公司关键转折和市场叙事变化，帮助用户理解“这一次可能并没有那么新”。

适用场景：

- 周期行业，例如地产、煤炭、钢铁、化工、半导体、航运、汽车。
- 技术替代或产业升级，例如 AI、云计算、新能源、消费电子。
- 监管变化明显的行业，例如互联网平台、教育、医药、金融。
- 市场情绪剧烈变化，叙事从极度乐观转向悲观，或反过来。
- 用户想知道历史上有没有相似情境。

资料偏好：

- 公司多年年报和关键公告。
- 行业历史数据、周期数据、价格数据、产能数据、库存数据。
- 历史新闻、历史研报、监管文件。
- 过去相似公司、相似行业、相似国家或地区案例。
- 股价历史走势只能作为背景，不得单独作为结论依据。

任务拆解要求：

1. 建立时间线：列出公司或行业的重要阶段和关键转折。
2. 寻找相似历史：至少尝试寻找 2 到 3 个可比较案例。
3. 比较相同点：当时和现在在需求、供给、政策、技术、估值、情绪上的相似处。
4. 比较不同点：这次有哪些结构性差异，不能机械套用历史。
5. 提炼历史教训：过去哪些判断后来被证明是错的，为什么错。
6. 给出当下观察指标：哪些信号可以验证历史类比是否成立。

报告章节要求：

- 历史时间线。
- 过去相似案例。
- 相同点与不同点。
- 历史教训。
- 当前阶段可能处在周期中的位置。
- 需要继续观察的历史验证指标。

关键问题清单：

- 这个行业或公司过去经历过哪些关键转折？
- 当前情况和历史上哪几次最像？
- 当时市场最初如何理解，后来发生了什么？
- 这次和历史相比，哪些条件已经不同？
- 历史上最大的误判来自哪里？
- 当前最像周期早期、中期、后期，还是完全不同的新阶段？
- 哪些数据能证明历史类比正在成立或失效？

自检标准：

- 必须同时写“相似点”和“不同点”。
- 不能只找一个历史故事就下结论。
- 历史案例必须服务于当前研究问题，而不是堆砌故事。
- 必须标出历史类比的局限性。
- 必须给出可以继续验证的指标。

禁止事项：

- 禁止简单写“历史总会重演”。
- 禁止把过去股价走势当成未来预测依据。
- 禁止只选择支持自己观点的历史案例。
- 禁止忽略制度、技术、竞争格局和宏观环境的变化。
- 禁止把历史类比写成确定性结论。

### 机遇预兆

代码标识：`opportunity`

核心目标：让报告更关注未来变化和潜在拐点，但不把希望写成事实。机遇预兆要强化趋势判断、催化因素、情景推演、先行指标和机会验证路径，帮助用户发现“可能值得继续跟踪”的方向。

适用场景：

- 用户想寻找潜在变化，而不是只复盘过去。
- 行业出现新技术、新政策、新产品、新需求或供给变化。
- 公司处在业绩拐点、产品周期、产能释放、出海扩张、组织调整阶段。
- 市场可能低估某些变化，但证据还不完全充分。
- 用户需要建立观察清单，而不是立刻做投资决策。

资料偏好：

- 最新公告、订单、产能、产品发布、管理层指引。
- 行业政策、技术路线、竞争格局变化。
- 上下游数据、价格变化、库存变化、招投标、渠道反馈。
- 研报中的盈利预测和关键假设，但必须谨慎对待。
- 新闻、电话会、专家访谈可以作为线索，但不能单独作为硬证据。

任务拆解要求：

1. 识别潜在变化：列出未来 6 到 24 个月可能影响研究对象的变化。
2. 区分事实和猜想：把已发生事实、正在形成的信号、尚未验证的假设分开。
3. 梳理催化因素：政策、产品、订单、价格、成本、竞争、资本开支、需求变化。
4. 建立情景推演：至少给出保守、中性、乐观三个情景。
5. 找到验证指标：列出后续跟踪哪些数据可以确认或否定机会。
6. 说明机会边界：机会成立需要哪些条件，哪些条件不满足就要降级判断。

报告章节要求：

- 潜在变化地图。
- 催化因素列表。
- 已发生事实、正在变化的信号、尚未验证的假设。
- 三种情景推演。
- 机会验证指标。
- 后续跟踪清单。

关键问题清单：

- 未来变化可能来自需求、供给、政策、技术、成本还是竞争格局？
- 哪些变化已经发生，哪些只是市场预期？
- 机会成立需要哪些关键条件？
- 哪些指标最早能验证机会是否兑现？
- 市场可能忽略了什么？
- 这个机会是短期催化、中期拐点，还是长期趋势？
- 如果乐观情景不成立，最可能卡在哪里？

自检标准：

- 必须明确区分事实、信号和假设。
- 必须给出至少 3 个后续可追踪指标。
- 必须写出机会成立的前提条件。
- 必须包含保守情景，不能只写乐观展望。
- 必须避免把“可能发生”写成“必然发生”。

禁止事项：

- 禁止空泛写“未来空间广阔”“有望受益”。
- 禁止只讲故事，不给验证指标。
- 禁止用单条新闻推导长期机会。
- 禁止把研报预测当成事实。
- 禁止给出买入、卖出、持有等投资建议。

### 深渊回响预兆

代码标识：`abyssal_echoes`

核心目标：让报告主动向下看，寻找风险、反方论点、估值陷阱、财务压力、叙事漏洞和最坏情景。深渊回响预兆不是为了悲观，而是为了避免报告只强化用户原本想相信的东西。

适用场景：

- 研究对象估值较高、预期较满、市场叙事很热。
- 公司处在高杠杆、高资本开支、高库存、高补贴或强周期环境。
- 行业政策、技术路线、竞争格局存在重大不确定性。
- 用户已经有偏乐观判断，需要反方检查。
- 公司财务、治理、商业模式或信息披露存在疑点。

资料偏好：

- 风险提示、年报附注、审计意见、关联交易、应收账款、存货、商誉、债务。
- 监管处罚、诉讼、质押、减持、重大客户或供应商变化。
- 竞争对手负面案例、行业下行案例、失败公司案例。
- 做空报告、反方研报、负面新闻可以作为线索，但必须交叉验证。
- 财务指标异常变化，例如利润增长但现金流恶化。

任务拆解要求：

1. 提取当前主流乐观叙事：先写清楚市场为什么看好。
2. 拆解关键假设：找出乐观叙事依赖的 3 到 5 个核心假设。
3. 逐条寻找反证：每个关键假设都要寻找可能推翻它的证据。
4. 检查财务和治理风险：现金流、负债、存货、应收、商誉、关联交易。
5. 构造最坏情景：说明如果关键假设失败，可能怎样传导到业绩和估值。
6. 给出风险验证清单：后续哪些数据恶化时需要提高警惕。

报告章节要求：

- 主流乐观叙事。
- 关键假设拆解。
- 反方论点与证据。
- 财务和治理风险检查。
- 最坏情景推演。
- 风险监控清单。

关键问题清单：

- 当前市场最相信的故事是什么？
- 这个故事依赖哪些关键假设？
- 哪些事实会推翻这些假设？
- 财务报表里有没有利润和现金流背离？
- 有没有高库存、高应收、高商誉、高负债或资本开支压力？
- 竞争对手、政策、技术路线是否可能改变格局？
- 最坏情景下，公司会先在哪个指标上出问题？

自检标准：

- 必须先写清楚乐观叙事，再写反方，不得只堆风险。
- 至少要拆解 3 个关键假设。
- 每个重大风险都要尽量对应证据或待验证数据。
- 必须包含财务层面的检查，不能只写宏观风险。
- 必须给出风险监控指标，而不是只写风险清单。

禁止事项：

- 禁止为了显得谨慎而罗列模板化风险。
- 禁止没有证据地暗示公司造假或违规。
- 禁止把任何负面新闻都直接当作确定事实。
- 禁止只写宏观风险，不检查公司自身经营和财务。
- 禁止把风险分析写成投资建议。

## 多预兆组合规则

用户可以同时选择多个预兆。多个预兆叠加时，Agent 不能简单把各自章节机械拼接，而要在报告开头说明本次研究的主要观察角度，并在报告结尾给出综合判断边界。

多预兆报告允许明显变长。用户选择多个预兆，本质上是在要求系统从多个研究视角完整展开，而不是把每个视角压缩成摘要。除非用户明确要求“简版”“摘要版”或设置篇幅上限，否则 Agent 应优先保证研究完整性、证据链和关键问题覆盖。

常见组合：

| 组合 | 适合场景 | 报告重点 |
| --- | --- | --- |
| 崇高预兆 + 深渊回响预兆 | 想深入研究一家热门公司，同时避免只看优点 | 一边拆商业模式，一边检查关键假设和风险 |
| 远古预兆 + 机遇预兆 | 想从历史周期中寻找未来变化 | 对照过去案例，寻找这一次可能不同的地方 |
| 崇高预兆 + 远古预兆 | 想系统理解行业长期演化 | 深拆行业结构，并放入历史周期中观察 |
| 机遇预兆 + 深渊回响预兆 | 想跟踪潜在机会，但不想忽略风险 | 同时列出机会验证指标和风险失效指标 |
| 四个预兆全部选择 | 重大研究对象或长报告 | 形成完整深度报告，但需要控制篇幅和结论边界 |

组合约束：

- 如果选择多个预兆，报告必须在开头列出“本次启用预兆”。
- 每个被选择的预兆都必须至少产生一个明确章节或子章节。
- 每个被选择的预兆都必须完整覆盖其关键问题清单，不能因为预兆数量增加而只保留一句概括。
- 报告可以很长；默认不为了缩短篇幅牺牲分析深度。
- 如果预兆之间出现冲突，例如机遇预兆发现乐观变化、深渊回响预兆发现重大风险，报告必须并列呈现，不得强行调和。
- 结论必须区分“较确定事实”“可观察信号”“待验证假设”“主要风险”。
- 不允许因为选择了机遇预兆就弱化风险，也不允许因为选择了深渊回响预兆就否定所有机会。

篇幅策略：

- 默认模式：完整报告。优先完整覆盖所有预兆，允许长文输出。
- 摘要模式：只有用户明确选择时才启用。摘要也必须保留每个预兆的核心结论、关键证据和待验证问题。
- 分层阅读：长报告可以在开头给出执行摘要，正文保持充分展开，结尾给出跟踪清单。
- 分段生成：如果模型或前端输出长度受限，可以先生成报告大纲和第一部分，再继续生成后续部分，不应直接删减重要视角。

## Agent 执行约束

研究报告 Agent 接收到预兆后，必须把预兆写入工作流状态，而不只是拼接到最终 prompt 中。

执行流程：

1. 规划阶段：根据预兆增加对应研究任务。
2. 资料阶段：根据预兆调整资料搜索和选择权重。
3. 分析阶段：按预兆要求回答关键问题。
4. 生成阶段：按预兆要求组织报告章节。
5. 自检阶段：逐项检查预兆是否生效。

结构化状态示例：

```json
{
  "omens": [
    {
      "id": "exalted",
      "name": "崇高预兆",
      "requiredSections": ["商业模式拆解", "利润与现金流驱动因素", "竞争格局与护城河"],
      "requiredChecks": ["解释关键指标含义", "区分利润与现金流", "列出待验证问题"]
    },
    {
      "id": "abyssal_echoes",
      "name": "深渊回响预兆",
      "requiredSections": ["关键假设拆解", "反方论点与证据", "最坏情景推演"],
      "requiredChecks": ["拆解至少 3 个关键假设", "检查财务风险", "给出风险监控指标"]
    }
  ]
}
```

报告生成后，Agent 应该输出预兆覆盖情况：

```json
{
  "omenCoverage": {
    "exalted": {
      "covered": true,
      "missingItems": []
    },
    "abyssal_echoes": {
      "covered": true,
      "missingItems": []
    }
  }
}
```

## 未来实现方式

第一版可以先把预兆作为前端多选项传给 Java 主后端，再由 Java 转发给 Python Agent 服务。

Python Agent 服务接收到预兆后，应当：

1. 在规划阶段调整研究任务。
2. 在搜索或资料选择阶段提高相关资料权重。
3. 在报告生成阶段增加对应章节。
4. 在报告自检阶段检查对应视角是否充分覆盖。

示例请求字段：

```json
{
  "target": "某公司或某行业",
  "reportType": "company_research",
  "omens": ["exalted", "ancient", "abyssal_echoes"]
}
```

## 与 PoE2 意象的关系

PoE2 中的预兆用于影响后续工艺或结果方向。Path of Market（市场之路）中的研究报告预兆也采用这个逻辑：用户不是直接要求一个固定答案，而是激活某些研究倾向，让报告更贴合当次研究目的。
