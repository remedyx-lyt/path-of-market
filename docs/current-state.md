### 1. 天齐锂业为什么失败（F13，最优先）

用户用“天齐锂业”（问题“公司详细情况。近期变化”，三个预兆）研究，任务失败：`MODEL_INVALID_RESPONSE`，7 次模型调用。会话记录 `storage/sessions/5568723e-….jsonl` 显示经过：

1. 找报告正常（2023–2025 年报 + 2026 年定期报告）。
2. 开始通读 2025 年报（245 页），每 20 页交给模型做一次阅读笔记。
3. 读到第 21–37 页这一批时，模型返回不完整，**整个研究直接失败**。

证据与修复：

- 会话末累计输出为 8,319 token；前六次成功调用合计 6,519 token，相减得到失败调用正好输出 **1,800 token**。旧代码阅读上限为 `min(1800, LLM_MAX_TOKENS)`。这强烈支持长度截断判断；旧事件没有保存 `finish_reason`，不能仅用耗时证明截断。
- 已确认异常边界有缺陷：阅读子调用的 `ModelServiceError` 直接穿透到整次任务；没有缩批恢复。现在有独立的 `LLM_READING_MAX_TOKENS=3600`，长度异常/连续格式失败时缩小失败批次，从同一页/字符位置重读，成功范围保留。临时连接/超时故障先同位置重试；仍失败回传带游标的工具错误，Agent 可补读、继续其他工具；未读范围不冒充完成。总运行预算与主动停止仍有效。
- 方法计划的两次旧回复未保存，**无法还原其具体校验原因**。现已记录逐次校验诊断并提供实际 schema、唯一短路径规范化和受控降级。现有 schema 本来就是 3–16 项，不能无证据把问题说成“上限 12 项”。
- 之前真实验收主要复用中际旭创阅读缓存；旧离线测试确有无缓存小 PDF，但未注入这类长度故障。不能说“从未测过无缓存”，也不能从一次失败推算新公司的失败率。
- 新增无缓存、245 页第 21 页故障恢复、同页字符游标接续、格式失败、临时超时、失败覆盖不增加、全局密钥错误、诊断落会话等回归。旧天齐会话保留为失败原始证据，不改写为成功。

### 2. 默认研究问题（F9）

页面一打开，“研究问题”框里就预先填好一段通用问题，不用自己敲。填研究对象、改截止日期、勾预兆时，这段问题自动更新，例如：

### 3. 表格不能因为“画图设置写错”就整张丢掉（F16）

现象：模型做了 9 张很有用的表（地区收入、产能/产量/销量/库存、客户集中度……），但“要画图的列”写成了列名或字符串（如 `["产量","销量"]`），而规定是列序号（如 `[1, 2]`）。程序校验时整张表判为不合格，连表带图一起丢了。

原则改为：**只要有数据，表格就一定保留。**

- 能确定意图的，程序直接改：列名换成序号，“1”换成 1，超出范围的列去掉。（这次那 9 张表都属于这一类。）
- 画图设置实在看不懂的：只是不画图，表格照常展示。不“坐标不对也先画上去”，错的图会误导读者。
- 行列数对不上的：能够确定列映射时补缺失格并注明；不能确定时保留异常说明，避免静默补齐或截断造成错列。
- 只有完全没有数据、或引用的页根本不是这次读过的资料时，才不放，并在时间线里写明原因。

### 4. 写正文失败后从头重写（F14、F17）

活动流里出现过“写作请求改用不带工具定义的方式重试”。现在的做法：整篇报告正文是一次请求一口气写完（边写边显示进度）。中途 DeepSeek 返回异常或输出不完整（截断、断线还是供应商报错，目前没记录下来），半截 JSON 没法用，程序就换一种请求方式从头重写，前面写好的部分作废。代价：白花一次写作的钱和时间；回退请求和研究阶段开头不一致，用不上缓存，更贵；回退那次也没有逐节进度。

这和 MCP 无关，接 MCP 也解决不了。改法分两层：

- **第一层：查清原因，尽量不出错（F14）**
  - 每次模型调用失败都记下原因：结束原因（截断/中断/报错）、错误码、已输出 token 数，写进事件与会话，活动流里显示。
  - 如果是长度不够，就提高写作输出上限。DeepSeek 单次最多能输出 38.4 万 token，现在只给约 2 万；加了表格、排版之后报告变长，很可能撞上了上限。
- **第二层：出了问题也不从头来（F17）**
  - **分节写**（推荐，更根本）：先定大纲，再一节一节写，每节单独请求。哪节出问题只重写那一节，其他保留；写完一节显示一节；报告再长也不受单次输出上限限制。代价是请求次数变多（每节一次，开头部分都能命中缓存，费用增加有限），要处理节与节的衔接。这本来就是 M2-6“分章续写”的内容。
  - **续写**：DeepSeek 有“前缀续写”（Chat Prefix Completion，目前 Beta，需走 `https://api.deepseek.com/beta`）：把已写出的部分作为助手回复的开头发回去，让模型从断掉的地方接着写。作为某一节内部的补救，需实测稳定性。

### 5. PDF 原页渲染（F18）

PDF 渲染供模型查看原页和自动核对主要会计数据使用。本轮实测确认：检查终端能找到 Poppler，但此前正在运行的 Python 服务的工具接口返回 `PDF_RENDERER_UNAVAILABLE`；这是**服务运行环境的 PATH 差异**，不是“本机没装”或“历史视觉能力从未成功”。

已采用固定版本 `pypdfium2` / Pillow，并在独立、可超时终止的 Python 子进程渲染；沿用原来的页码、PNG 尺寸/大小与缓存校验契约。启动脚本检查这两项依赖，空 PATH 渲染也有回归。渲染成功不等于模型已理解图片；本轮不调用真实视觉模型。

## 系统现在能做什么

网页输入 → Java 异步任务 → Python `AgentRunner`：按问题/预兆完整读取相关原版方法并形成计划 → 模型循环调用六个逻辑工具（找报告、完整阅读与回查、行情、原页视觉、读方法、正文取数）→ 程序核查引用/覆盖/图表/预兆章节 → 写正文、生成数据表、复核 → 网页展示章节、引用、财务/业务/研发图、数据表、行情图、预兆覆盖。研究中右侧实时显示过程；研究逐条写入会话 JSONL，重启后可打开。底层八个工具。
