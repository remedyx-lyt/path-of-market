# 稳定性审查与恢复修复（2026-10-24）

## 结论

项目已是可以运行的早期财经研究 Agent：React → Java → Python，模型会选择工具、读工具结果并继续行动；有自动发现报告、全文分批阅读、行情计算、Skill 方法计划、财务/业务表图、活动流和会话保存。分层方向成立，不需要推翻原产品设计。

它尚不能称为稳定日用产品。最近增加了资料范围、预兆、表格、视觉与复核，但失败恢复、输出契约和验收样本没同步补齐；“功能已实现”被混同为“各种输入均已稳定”。不能把这次失败归咎于用户问题太简单，也不能仅用“项目复杂了”解释。

本轮先修已复现的故障边界，保留六个逻辑工具与现有框架；没有接入新的研究功能、聊天或多 Agent，没有改写旧失败会话，也没有重生成付费报告。

## 天齐锂业失败：能证明什么

原记录：`storage/sessions/5568723e-0968-4ca0-8637-f4ddf1251916.jsonl`；运行 ID `160b53d5-44cd-4587-9082-fb0392e2089f`。

| 位置 | 记录与代码证据 | 判断 |
| --- | --- | --- |
| 研究方法计划 | 第 1、2 次调用均有成功响应，随后 `methods_plan_failed` | 两次输出未通过计划校验；旧记录没保存原回复/字段错误，无法还原具体哪条规则 |
| 资料发现 | 找到候选年报和当期报告，开始处理 245 页的 2025 年报 | 公司识别、发现、下载和文本解析并非本次最终失败点 |
| 原文阅读 | 第 1–20 页经历一次笔记修正后被计入覆盖；第 21–37 页对应第 7 次模型调用后直接 `run_failed` | 停在阅读子流程，尚未到完整报告写作与制图 |
| 输出长度 | 总输出 8,319 − 前六次成功调用 6,519 ＝失败调用 1,800 token；旧阅读预算 `min(1800, LLM_MAX_TOKENS)` | 强烈支持输出撞顶判断；旧事件缺少 `finish_reason`，不能假装有完整直接证据或仅凭耗时断言 |
| 异常处理 | `batch_note` 只捕获解析 `ValueError`，`ModelServiceError` 穿透到主循环 | 已确认的程序缺陷：单批模型失败直接终止整次研究，无缩批恢复 |

方法计划失败已走备用流程，不是第 7 次调用终止的直接原因。没财务图是研究还没走到取数/制图阶段的结果，不是用户必须自己准备 Excel。

旧离线测试确实有无缓存的小型 PDF，但没有注入这类阅读长度故障；最近真实案例主要复用中际旭创阅读缓存。因此“67 项测试都绿”没有排除这个故障。不能从这一个样本推算新公司的失败率。

## 已修改的恢复机制与入口

| 修改 | 程序入口 | 行为与边界 |
| --- | --- | --- |
| 阅读输出预算独立 | `apps/agent/app/core/config.py`、`.env.example`、`services/agent_runner.py::model` | `LLM_READING_MAX_TOKENS` 默认 3600；简单模型报告的 `LLM_MAX_TOKENS` 不再卡住通读笔记；正文仍有自己的预算 |
| 失败批次自动恢复 | `services/runner_reading.py::read_all_batches` | 长度异常或两次格式失败时缩小页数/字符批量，从失败的同一游标重读；成功范围不回退；可把一页拆成多个字符片段，直到完成 |
| 临时失败可继续处理 | 同上、`agent_runner.py::run_tool_call` | 阅读暂时超时/连接/上游错误先同位置重试；仍失败形成含游标和覆盖的工具错误，Agent 可以继续补读或使用其他工具；主循环不因这类单工具错误立刻死亡 |
| 覆盖真实性 | `runner_reading.py`、`runner_report.py::validate_content` | 笔记未通过校验，游标与已处理字符/页数不前进；未读完的资料仍不能冒充完整研究。认证/余额/限流等全局问题、总预算或主动停止仍能结束任务 |
| 调用失败诊断 | `agent_runner.py::model`、`model_json.py::validation_problems` | `model_failed` 记录调用序号、用途、错误码、结束原因、输出预算、供应商用量、耗时；供应商没有提供的用量不猜。字段校验只记录位置/错误类型，不回显整份资料 |
| 方法计划改进 | `runner_methods.py::prepare_methods` | 逐次诊断，提示中给出实际 Pydantic schema，唯一短参考路径可展开；不接受未提供的参考或未选择的预兆。失败可降级，不再无诊断；没有凭猜测改大 16 项上限 |
| 活动流如实结束 | `apps/web/src/features/research-lab/ActivityPanel.tsx`、`ResearchReport.tsx` | 显示缩批/重试/校验失败；停止后工具/模型不继续转圈；失败计划不再同时显示“已形成计划” |

恢复不是将整个研究清零重跑，也不是把失败范围静默跳过。已经通过校验的内容保留；仍无法读取的批次带游标交回 Agent。当前尚无跨进程的任务检查点接续，不能把“同一次运行内接续阅读”说成“服务重启也能接着跑”。

### 同时确认并修复的三个错误

- `runner_report.py::review`：复核稿在校验后改变章节数量时，原代码虽然标记“丢弃”，变量却已经指向复核稿；现在只有复核全部接受后才替换，原报告和表格保留。
- `SessionStore.java::append`：原代码在整批校验和写盘成功前更新去重集合；后续校验或写入失败，重试可能被错误去重。现在先暂存集合，写盘后更新；IO 失败时下次从磁盘重建。
- `report_figures.py::NUMBER`：自主表格数字匹配丢失负号，可能把 `-100.5` 错配成 `100.5`；已保留负号并加反例回归。数字同页出现仍不等于指标/年度/列序已独立审计。

### PDF 渲染（F18）

实测出现环境差异：检查终端的 `pdftoppm` 能渲染，而原 Python 服务 `/tools/execute` 返回 `PDF_RENDERER_UNAVAILABLE`。原文档“本机缺 Poppler”“原页视觉一直没生效”表述过度；应区分具体服务进程和历史已成功的视觉运行。

`tools/visuals.py` 现调用 `tools/pdf_render_worker.py`，使用固定的 `pypdfium2==5.14.0` / `Pillow==13.0.0`；子进程隔离、30 秒超时，继续校验 PNG 尺寸/大小、页码、哈希与缓存。`requirements.txt` 与启动依赖检查已更新。无 Poppler/PATH 也能渲染，已有 PNG 可复用。

运行中的三服务已重启并检查；真实工具接口已成功渲染天齐 2025 年报第 9 物理页（1272×1799）。这是本地渲染验证，本轮没有调用视觉模型，也不宣称图片内容已由模型理解。

## 为什么慢，优化先做哪里

以已有中际旭创成功会话 `1717e236-6ec1-4486-81a4-d48e3faf94d2.jsonl` 为例，不重新付费测试：21 次调用，968,705 token；46 批阅读笔记命中缓存。

| 已有调用类别 | 成功调用数 | 累计调用耗时 | 输入 / 输出 token |
| --- | --- | --- | --- |
| 主循环决定下一步 | 13 | 约 22.6 秒 | 617,071 / 1,824 |
| 正文写作 | 2 | 约 88.4 秒 | 149,244 / 15,537 |
| 数据表 | 2 | 约 29.4 秒 | 149,924 / 6,229 |
| 复核 | 1 | 约 25.9 秒 | 17,084 / 7,342 |

另有提取数据与未成功调用；以上是对应成功模型调用累计耗时，不是整次运行的完整耗时。记录中有两次写作请求回退、一次报告校验失败和一次丢表事件。旧日志缺少失败调用诊断，不能断言回退全部因长度截断。

真正应优化的是无效重复：整篇 JSON 写作/复核、机械格式错误导致整篇重写、画图字段错导致整张表作废；单纯把上下文翻倍、工具增加或无限放大输出上限不能解决。当前修复减少已知的失败重读和错误替换，**未做同任务真实前后对照，不能宣称速度已经提升某个百分比**。

## 当前完成程度与剩余问题

| 能力 | 当前程度 |
| --- | --- |
| 模型 → 工具 → 结果 → 再决策 | 已实现动态 Agent 主循环；不是只包一次 API |
| 全文资料与行情 | 沪深公司官方定期报告、连续文本阅读、关键词/按页回查、原页渲染/视觉入口、日线与程序计算已有 |
| Skill / 预兆 | 选择/读取原版方法、计划、写作、覆盖自检已接；效果检查仍含模型自评与关键词检查，不代表方法全部充分落实 |
| 图文报告 | 已有金额/同比/业务结构/研发等图、自主表格、引用与标签开关；自主表格仍有格式脆弱和公式核验缺口 |
| 会话 / 记忆 / 恢复 | JSONL 保存、最近研究、重启查看已有；长期研究记忆、compaction、分支对话和任务崩溃后接续尚未实现 |
| 生产可靠性 | 早期原型；仍需多公司、多文档排版、冷/热缓存、错误注入和小预算真实验收，不能凭单一公司反复成功算稳定 |

另外记录为下一步验收项：

- **F16**：`chartColumns` 用列名/字符串就可能丢整表。可确定的格式应修复；含义不明时保留表格与问题说明、取消画图。不能用静默补格/截断掩盖错列。
- **F17**：正文与数据表仍整份输出；应先大纲/稳定章节 ID，再按节保存，失败只恢复相关节，最后整合核查；聊天前优先处理。
- 自主表格的核对只证明数字在所引页出现（含单位换算），不是完整财务语义核验；未匹配/模型计算的格子仍可能画图。下一项需明确原值/计算值、公式和核验状态，防止未核验值进入正式图。
- F5 的产能/产销列表已实现，但利用率/产销率没有独立确定性公式校验，任务板改为部分完成。
- JSONL 主循环消息/事件/报告已有；辅助方法/阅读/写作子调用未全部保存原始消息，旧格式故障未必可精确重放。保存会话与保存任务检查点是两件事。
- UI 仍写“公司或板块”，实际工具主要支持沪深单公司；行业/新闻/政策、完整外部研报搜索仍未接入。能力声明后续需与支持范围一致。
- `merge_extra_sections` 对合并正文仍有 10000 字符上限，不能将“合并后正文全保留”当作无限保证；分节生成时一并替换。

## 下一步顺序与开发纪律

1. F16：修自主表格的结构容错与核验状态，保证有用表格不因画图设置丢失，同时拒绝误导的图。
2. F17：分节生成与保存成功章节，失败按节恢复，减少长报告整篇返工；维持原产品的财经研究逻辑。
