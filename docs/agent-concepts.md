# Agent 基础概念

## 本项目的研究 Agent

工作台是整个产品，研究 Agent 是内部完成研究任务的能力模块。它根据目标、预兆和已有证据，选择下一步工具；工具返回结果后，再决定是否补查、对比或结束。

```text
目标与研究状态 → 模型选择动作 → 程序执行工具 → 更新证据 → 模型继续判断
```

框架本身可以有固定的执行循环和校验规则；真正要动态变化的是由模型决定的研究动作。一个模型配合几个工具就能实现该能力，不要求先构建多 Agent 系统。

定时运行、调用一次行情 API、切换几个提示词或固定 RAG 流程，单独看都不能证明这一动态行为。M0 的 mock 报告只验收服务接口；M1 必须使用真实资料和真实工具执行记录验收 Agent。

参考：[Anthropic 对工作流与 Agent 的定义](https://www.anthropic.com/engineering/building-effective-agents)。

## LLM

大语言模型负责理解问题、总结材料、基于证据推理，并生成研究报告。

## Tool Calling

工具调用让 Agent 能做模型本身做不了的事情，例如网页搜索、读取文档、查询行情、保存笔记、对比公司。

模型提出工具名称和参数，程序检查后执行。工具结果携带资料来源、日期、页码或指标口径，再交回模型。数值计算由工具执行，不依赖模型直接猜算。

## RAG

RAG 是“检索增强生成”。它的意思是：系统先从用户自己的文档和历史研究里找相关资料，再把这些资料交给模型回答。

检索可以作为研究 Agent 的工具：模型选择查询对象和问题，阅读返回证据，再决定是否补查原文。RAG 是取证能力，不要求训练模型；结构化行情和财务数据可通过数据库查询和计算工具直接使用。

## Memory 记忆

Path of Market（市场之路）需要两类记忆：

- 用户记忆：投资风格、关注板块、观察池、分析偏好。
- 研究记忆：研究报告、引用来源、核心假设、后续问题。

## Workflow 工作流

工作流是一套固定的研究流程。例如深研室做公司研究时，应该稳定输出业务概览、财务表现、竞争格局、增长逻辑、风险点、市场分歧和后续问题。

在本项目中，Agent 工作流主要放在 `apps/agent/app/services/workflows`。Java 主后端不直接写复杂 Agent 推理逻辑，而是通过 HTTP 调用 Python Agent 服务。

报告格式、日期过滤、参数校验和步数限制可以固定；资料选择、调查顺序、缺口处理由研究 Agent 结合状态决定。业务中的固定流程与研究 Agent 可以共同存在。

## Data Provider

Data Provider 是数据源封装层。上传文件、搜索结果、yfinance、AkShare 或付费 API 都应该被包装成可替换的数据来源，避免上层业务直接依赖某一个网站或接口。

## Scheduler 调度器

调度器后续会负责运行追猎者任务，例如每日更新、每周总结、公告检查和提醒任务。

调度器负责何时触发；研究 Agent 负责触发后哪些变化值得调查、用什么工具查证。消息推送是结果传递能力，不等同于研究决策。

## 预兆与 Skill

四个预兆定义研究策略，具体规格见 `report-omens.md`。策略要影响调查问题、资料选择和检查项；只调整输出语气不足以完成规格。

研究 Skill 可以封装这些方法，但数据访问仍依赖实际工具和授权。工作台和通用 Agent 应复用同一套资料工具，避免分别维护两份研究实现。项目开发 Skill 则用于开发流程和文档交接，二者用途不同。

## Agent 运行记录与验收

记录研究对象、截止日期、启用预兆、实际工具名称和参数、返回证据、资料缺口和停止原因。展示可核查的执行摘要，不要求公开模型内部思维过程。

M1 至少验证：不同问题产生不同工具动作；证据冲突触发补查；缺少资料时报告缺口；达到预算或超时限制时停止。任务状态和来源必须反映实际执行，不能用演示内容冒充真实研究。

## Java 主后端与 Python Agent 服务

- Java 主后端负责稳定的业务系统：接口、数据库、用户画像、研究日志、观察池、任务状态。
- Python Agent 服务负责 AI 能力：模型调用、RAG、文档解析、网页搜索、行情工具、研究工作流。
- 这种拆分适合边学 Java 后端边做 AI 项目，也接近真实公司的多服务架构。
